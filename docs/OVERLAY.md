# Overlay

One topic model, two repos: this one is the reusable half, yours is the
personal one. This guide is for someone who cloned this repo and wants to
keep their private configuration separate — it assumes no specific overlay;
`~/.dotfiles-private` is the example path used throughout (any path works).

## Why an overlay

This repo is the **plumbing**: generic, reusable, publishable. An overlay is
the **policy**: everything tied to one person. Where a file goes:

| Goes public if… | Goes in the overlay if… |
|---|---|
| a stranger could reuse it as-is | it is tied to you, an account, or one environment |
| it holds no secrets | it holds credentials, hosts, or personal device settings |
| it works anywhere | it only works on one machine or inside one editor profile |

One rule: **if you would hesitate to publish it, it belongs in the overlay.**

## The mechanics are copyable

`script/bootstrap` and `script/gate.sh` are repo-agnostic — bootstrap resolves
its root from its own path and discovers topics by walking the tree — so copy
both verbatim into the overlay's `script/`. `script/install` is the same
walker plus a Brewfile step: copy it and trim what the overlay does not have,
and expect it to drift from this repo's version as either evolves.

Keep the conventions: `script/` and `docs/` are never topics, everything else
is. And **prefix your gate keys**: all gates — both layers — keep state in a
single `~/.local/state/dotfiles/gate-<key>/` directory, and `brew`/`apt` are
already taken. Note that the *Force everything to re-run* recipe in
[MAINTENANCE.md](MAINTENANCE.md) resets that directory, both layers with it.

## Apply order

Public first, overlay second. The two bootstraps know nothing about each
other, and on a shared target the last apply wins silently:

```sh
~/.dotfiles/script/bootstrap && ~/.dotfiles/script/install        # 1. plumbing
~/.dotfiles-private/script/bootstrap && ~/.dotfiles-private/script/install  # 2. policy
```

To update the overlay, reuse the public wrapper — `bin/dot` honors
`DOTFILES`:

```sh
DOTFILES=~/.dotfiles-private ~/.dotfiles/bin/dot
```

Both layers back conflicting targets up into the same
`~/.dotfiles-backup/<stamp>/` tree; only the timestamp tells them apart.

## The rule: disjoint file sets

The overlay must never manage a `$HOME` target this repo already manages —
a collision means one apply silently clobbers the other. Audit after adding
files to either repo; this must print nothing:

```sh
managed() {  # managed <repo> — every $HOME target a bootstrap would own
  "$1/script/bootstrap" --dry-run \
    | grep -E '^(OK|LINK)' \
    | sed -e 's/^LINK [^>]* -> //' -e 's/^OK  *//' | sort -u
}
comm -12 <(managed ~/.dotfiles) <(managed ~/.dotfiles-private)
```

The audit parses each bootstrap's `--dry-run` plan, so it compares resolved
`$HOME` targets rather than repo-relative source paths: `git/config/x.symlink`
in one repo and `editor/config/x.symlink` in the other collide at
`~/.config/x`, and only the resolved view sees it. The `darwin/`/`linux/`
subtrees are handled for free; run the audit once per OS you use. It works
before the first apply (all `LINK` lines) and after it (all `OK` lines).

## Public extension points

What this repo deliberately leaves open for an overlay to hook:

| Extension point | What it is | Overlay usage |
|---|---|---|
| `~/.localrc` | 0600, never committed, sourced first by zsh (`zsh/localrc.example` is the template) | secrets and overlay flags live here |
| `~/.gitconfig.local` | generated by the public bootstrap | never manage or regenerate it |
| `DOTFILES_SKIP_VSCODE_EXTENSIONS=1` | opt-out of the public VS Code extension set | unset means both sets apply; the overlay's own `vscode/install.sh` owns its list |
| tmux `prefix C-n` | runs `~/.local/bin/tmux-notes` when that file is executable, otherwise a silent no-op | overlay or machine provides the script, deliberately unversioned |
| `DOTFILES_*` flags | public names documented in `zsh/localrc.example` | define yours with the same prefix; never reuse a public name |

**Coordinated installers.** The same topic may exist in both repos with
different inputs: this repo's `vscode/install.sh` installs the generic
extension list, the overlay's installs the personal one — disjoint lists,
separate skip flags. It is the one pattern where the split needs an explicit
pair; everything else is disjoint by construction.

## Secrets

No secret in either repo, public or overlay. Endpoints and keys are
environment variables in `~/.localrc`, read at run time by installers;
hash-gates record a sha256 of their input file, never its content. Run your
own secret scan before every push of the overlay — this repo's CI runs
gitleaks on every push (see *Before pushing* in [MAINTENANCE.md](MAINTENANCE.md)).

## Patterns worth adopting

Three scripts earn their keep once an overlay grows, in rough order of
payoff:

- **A guided `setup`** — one command narrating its phases (prerequisites →
  reconcile → link → install → check), idempotent, so that re-running it is
  the update path. On first contact with a machine that has no
  `~/.localrc`, stop after seeding a commented 0600 skeleton.
- **A `doctor`** — one `ok`/`TODO` line per concern (links applied,
  variables set, tools present), each `TODO` with the exact fix. It prints
  the *names* of missing variables, never their values, and changes
  nothing.
- **An `adopt`** — before the first link, reconcile pre-existing live files
  with the repo versions, one prompt per file: merge JSON (recursive union,
  the live side wins scalar conflicts), keep live, keep repo, or diff —
  with a batch-answer variable for scripted runs and report-only behavior
  without a tty. Bootstrap's backup policy remains the fallback.

## Rules recap

1. The overlay applies second, always.
2. Disjoint `$HOME` targets — the audit above must print nothing.
3. No secrets in either repo; `~/.localrc` is their only home.
4. Prefix gate keys; gate state is shared with this repo.
5. Prefix overlay flags `DOTFILES_*`; never reuse a public name.
